# Validation

Run `npm run check` and `npm run pack:check`. Tests use disposable directories and do not require credentials. The real-core test is opt-in:

```sh
DSH_MEMORY_RUNTIME=/path/to/request-assembly-enabled/runtime \
DSH_MEMORY_TAVERN=/path/to/tavern \
node --test test/host-integration.test.mjs
```

This loads actual DSH Cordis, Session, AgentLoop and Tavern modules. A synthetic provider captures the final request; assertions check content, resource/config revisions, source disposal and preserved native history. It is not an external-provider/network-delivery test. A stock core without request assembly protocol 1 does not satisfy this test.

For actual installation acceptance, use a separate `DSH_HOME`, install this package with `dsh plugin --profile web add`, and start a loopback Web Host. Install the official `dsh-skill-filesystem` provider against a disposable SKILL.md directory, then verify both catalog and exact body through `/api/dsh-memory-manager/query` and `/read`. Merely registering a fake adapter or seeing an empty catalog is insufficient.

Compatibility must be recorded separately for the manager and request injection. The standalone manager, native Settings/header panels and filesystem Skill reads work on stock DSH 0.2.0-rc.2. That stock release does not expose request assembly protocol 1: applying a Tavern assembly preset returns `REQUEST_ASSEMBLY_CORE_REQUIRED`. Full Tavern/MVU request injection requires the existing prepared Session and AgentLoop builds described by Tavern's `docs/REQUEST_ASSEMBLY.md`; these are development core extensions, not an unmodified official release. Record the resolved runtime paths, versions, hashes and build receipt, and verify the complete Web dependency graph before acceptance. Do not enable a capability flag without the matching implementation. Keep the stock rejection evidence alongside prepared-core success.

For an isolated browser run, use a self-authored card, a separate DSH_HOME and a synthetic model endpoint that never falls through to a real provider. Check code review and separate write authorization, missing/denying manager policy, trusted patch/replace, CAS and revocation without false notifications, restored empty sessions, the first actual assembled request, and invalidation of the previous initial binding. Host title generation may make an additional model call; distinguish it from the conversation turn using durable events. Capture the actual request and its source revision; allow/preview results are insufficient. Ordinary visible dynamic DOM checks do not establish every geometry boundary. Disclose any explicitly blocked or unrun checks instead of retrying them through another route.

For Tavern co-install acceptance, install the intended Tavern build in the same isolated profile, configure the optional loopback base URL, create/import a disposable world book through Tavern's public API, explicitly bind it to a disposable session, and read its body through the manager. Confirm that read-only capabilities, scope and the absence of unproven application events remain accurate. Do not use `/active` preview as historical evidence.

For browser acceptance, inspect the native Settings section and session header action in a real DSH browser: filters, empty/error states, resource reads, supported edits, configuration provenance, session switching and unload. Build success and server-rendered markup do not establish browser acceptance. Distinguish browser navigation failures from explicit tool or approval denials. Preserve the exact available error and its provenance; do not infer a security denial from a browser error code alone. An explicitly authorized isolated headless browser may exercise the real Host with a fresh test profile and normal browser security. Never bypass an explicit access denial. Record the stable run console separately from intentional Host restarts and negative tests.

MVU acceptance requires the integrated source build exposing `tavernMvu` v1. Test shared IDs across sessions, copy/new IDs, source CAS/idempotency, management ownership loss/error/unload, completed-final-message gates and genuine request evidence. Adapter fixtures alone do not establish this integration. TaskSystem is not implemented by this package.

Keep run-specific logs, screenshots, local paths and private data in ignored `.local/`. Before publication, independently verify the current Awesome contribution rules and public repository age, real commit count, topic and description. Never manufacture commits to pass an external gate.

## Frozen MVU source integration

Set `DSH_MEMORY_MVU=/absolute/path/to/frozen/tavern-checkout` and `DSH_MEMORY_RUNTIME` to the request-assembly-enabled DSH runtime, then run `node --test test/mvu-integration.test.mjs`. The test imports the actual public MVU service and Tavern Host integration from that checkout without modifying it. It uses temporary stores, self-authored resources and a synthetic grant authority/provider; it runs no user card scripts and uses no external credentials.

The checks cover cross-session current identity, source CAS/copy/mode APIs, explicit authority rejection, card policy plus separate grant, patch/replace/schema behavior, source idempotency and commit facts, manager unload, caller cancellation and grant revocation during the final awaited scope read. A real DSH AgentLoop test observes MVU text in the captured provider request, source request/state facts, and managed fail-closed behavior after manager removal. These are source API and actual-core Host checks, not browser/renderer binding acceptance or proof of external-provider delivery. Record the source commit and clean-worktree status with every run; repeat against the selected final merged build.

The MVU integration suite also pauses an actual source transaction during policy evaluation and during its final scope read, writes a denying configuration file and awaits `manager.reload()` without re-registering the handler. Resuming must reject, preserve source revision/content and emit no applied fact. This regression fails on MVU 3cb2acd; it requires the source-side synchronous policy lease fix and must not be skipped or weakened to accept the old candidate.

Condition-lifetime regression must unregister and re-register the same ID and function after obtaining a policy decision. The old lease must stay false, the old disposer must not remove the new registration, and an actual source transaction paused in its final scope await must not commit after this change. Initial-binding integration uses the actual MVU Host, PlayWorkspaceStore, PlayMembershipService and SessionSelectionStore with a synthetic grant authority. It preserves the explicit initial scope, shared current state and manager policy with the four metadata events observed in an official newly created RP session. Detaching membership and restoring identical catalog bytes through source CAS must not revive an old capability; a fresh binding can be created, and the first turn invalidates it. The membership lease must come from the real store, never a constant-true stub. This does not replace renderer binding acceptance.

For narrow browser checks, use both a desktop viewport and 390px width. Verify both the resource panel and native Settings navigation remain usable without horizontal overflow. The manager scopes its narrow Settings adjustment to the native dialog while this section is mounted; other Settings sections retain Host styling. Check the real HTTP poll stream after closing either panel, and verify a session switch closes the old overlay before reading the new scope.
